# demoqa.com: Cypress UI and API automation

Cypress and JavaScript suite covering the key user interactions on
[demoqa.com](https://demoqa.com): a multi-control form, a CRUD table with search and pagination,
native browser dialogs, modals, custom dropdowns, and the Book Store both anonymously and signed in.

**71 tests, all passing** against the live site, plus a ticket-style write-up of the **8 bugs**
found while building it. See [BUGS.md](BUGS.md), the one-page [REPORT.md](REPORT.md) and
[RECOMMENDATIONS.md](RECOMMENDATIONS.md).

## Install

```bash
npm ci
```

## Run

```bash
npm test                 # headless, whole suite, the single command to run everything
npm run test:headed      # headed Chrome, useful while developing
npm run open             # interactive Cypress runner
npm run test:ui          # browser specs only
npm run test:api         # API specs only, no browser, a few seconds
npm run test:no-signup   # everything except the specs that create an account
npm run test:smoke       # @smoke subset across both, ~25s
npm run test:spec -- cypress/e2e/ui/web-tables.cy.js   # one spec
```

Point the suite at a different environment without touching code:

```bash
CYPRESS_BASE_URL=https://staging.example.com npm test
```

Code quality (optional tooling):

```bash
npm run lint
npm run format
```

`cypress/reports/`, `cypress/screenshots/` and `cypress/videos/` are generated and git-ignored. The
`artifacts/` copies are committed so results can be read without running anything. Open
`artifacts/cypress-report.html` in a browser for the full report, with per-test steps, durations and
any failure screenshots embedded; GitHub shows it as source rather than rendering it, so clone or
download it first.

In CI the same artifacts are uploaded by the workflow in
[`.github/workflows/e2e.yml`](.github/workflows/e2e.yml), which runs the suite on every push and
pull request.

## Design decisions

**Page objects own selectors, specs own intent.** Every page object exposes an exported
`selectors` map and intent-revealing methods (`addRecord`, `setDateOfBirth`, `submittedValues`).
Specs read as user behaviour and contain no CSS. When the DOM changes and demoqa's Web Tables
page _has_ been rebuilt from React-Table to a plain Bootstrap table, which breaks most tutorials
for this site, the fix is one line in one file.

**Assertions are about data, not layout.** The practice form's confirmation table is read into a
`{ label: value }` object, so the test asserts "Gender is Male" rather than "row 3 column 2".

**Resilient locators.** IDs where the app provides stable ones; otherwise a row is found by its
content (`tr:contains(email)`) and the action button is scoped inside it, so a test never
depends on row order, on pagination, or on record numbering.

**No fragile waits.** There is not a single `cy.wait(ms)` in the suite (`cypress/no-unnecessary-waiting`
is enforced by ESLint). The 5-second delayed alert, for example, is asserted with a retrying
assertion on a stub, which passes the moment the alert fires and still fails loudly if it never does.

**Generated test data, constrained to what the app accepts.** `dataFactory.js` builds records with
[`@faker-js/faker`](https://fakerjs.dev), so no two runs use the same data and no spec depends on
another's leftovers. The builders generate _within_ the app's constraints, field maxlengths, the
fixed subject/hobby lists, valid state→city pairs, because a builder that emits data the form
rejects produces failures that say nothing about the application. Every builder takes overrides, so
a spec states only the field it cares about. Web Tables state resets on reload, so no cleanup is needed.

**Bugs are reported, not encoded as tests.** The suite covers the behaviour the app is supposed
to have. Where it does something wrong, that goes in [BUGS.md](BUGS.md) as a ticket, summary,
steps, expected vs actual, evidence, severity, rather than into an assertion that documents the
broken behaviour as if it were correct. Where a test has to route around a bug it says so and
links to the ticket: the practice-form happy path dismisses the confirmation with Escape, because
BUG-002 means the Close button does not work.

**Tagged runs for fast feedback.** Core paths are tagged `@smoke` via
[`@cypress/grep`](https://github.com/cypress-io/cypress/tree/develop/npm/grep), one per page,
11 tests in ~30 seconds against the full suite's ~2 minutes. CI runs smoke first as a gate, then the full suite, so a
broken build fails in under a minute. Everything untagged is the regression set: tags mark the fast
subset rather than labelling all 71 tests.

## Flakiness: what I hit and how I handled it

| Symptom                                                                | Cause                                                           | Handling                                                                                                                                                                                      |
| ---------------------------------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Random slow loads, layout shift, occasional cross-origin script errors | demoqa wraps every page in Google ad/analytics bundles          | Blocked at the network layer via `blockHosts` in `cypress.config.js`, the whole suite got faster and stopped shifting under the cursor                                                        |
| "Element is covered by another element" on Submit                      | Ad slots reserve fixed banner space even when the ad is blocked | `scrollBehavior: 'center'` plus a `suppressAdSlots()` command that injects CSS to hide the leftover ad containers, the app's own DOM is never mutated                                         |
| Tests failing on third-party script errors                             | Ad scripts throw inside the page                                | `uncaught:exception` is handled **by pattern** in `support/e2e.js`, never with a blanket `return false`, so a genuine application error still fails the test                                  |
| `TypeError: Lr.findDOMNode is not a function`                          | Not flake, a real application bug (BUG-002)                     | Reported rather than suppressed; the happy path dismisses the modal the way a user still can (Escape)                                                                                         |
| Public demo site is occasionally slow                                  | Shared free infrastructure                                      | `retries: { runMode: 2, openMode: 0 }` and generous-but-bounded timeouts. Retries are deliberately CI-only: a test that passes on retry is still reported and treated as a signal, not hidden |

Across the runs done while building this, the only non-deterministic failures came from the ad
stack; after `blockHosts` was added, the main suite has been stable run to run.

Tests that create an account on the live site are tagged `@creates-account`, the signed-in specs
and the account-lifecycle API specs. `npm run test:no-signup` runs everything else, which is useful
when you would rather not add users to a shared demo server. Each API block deletes the user it
created.

Registration through the UI form is deliberately not automated. The page carries an invisible
reCAPTCHA v3: it does not block a real browser, but inside Cypress the token never resolves, the
form silently does nothing and stubbing `window.grecaptcha` to get past it was flaky at roughly one
run in three. Accounts are created through `POST /Account/v1/User`, which has no captcha and the
form's client-side validation is covered separately.

Deliberately out of scope: drag-and-drop widgets, frames and window handling, they add runtime
without adding much signal for this exercise.
